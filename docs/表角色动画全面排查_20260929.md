# 表角色动画全面排查

日期：2026-09-29。范围：当前 `src/main/resources/img/char/spine/` 的全部 12 个动画。此次是排查与证据导出，未修改正式资源、Java 播放逻辑或部署 JAR。

## 结论

不是单纯的“GIF 看着有毛边”或“某帧没对齐”，而是三类问题叠加：

1. **9 个旧动作的纹理 Alpha 格式不符合游戏渲染方式。** 原版 `AbstractCreature` 的静态初始化对 `SkeletonMeshRenderer` 调用了 `setPremultipliedAlpha(true)`；而这 9 个动作仍保存普通 Alpha 颜色。半透明边缘会被游戏过度叠加，粉紫残留、白边和亮边因此被放大。普通 PNG 查看器正确乘 Alpha，可能看不出相同程度的问题。
2. **各动作使用的 idle 参考不是完全相同版本。** 部分首尾人物高度、脚底、脚距和姿势与当前修鞋后的 idle 不同；仅修坐标或仅把最后一帧换成 idle，并不能保证整段自然。
3. **GIF 另有调色板与透明表示问题。** 不应拿透明 GIF 当作 RGBA PNG 或游戏渲染的准确替代品；旧导出还存在时长取整错误。

## 1. Alpha 格式问题的直接证据

预乘颜色必须满足 RGB 通道不大于 Alpha（允许极小的量化误差）。以半透明区域统计：

- hurt 第一帧：4181 个半透明像素，其中 2961 个违反该约束，约 70.82%。
- cast_special 第一帧：3826 个半透明像素，其中 2916 个违反约束，约 76.22%。
- idle、当前 cast_prayer、death 的扫描结果符合预乘格式。

`alpha_blend_comparison.jpg` 左列按普通 PNG 的正确 Alpha 显示，中列按游戏预乘混合公式模拟，右列显示差异放大 4 倍。差异集中在轮廓、头发、衣服和剑边缘，解释了“单帧正常，动起来/游戏里出现杂边”的一部分。

这是根据原版字节码和实际纹理生成的混合模拟，不是游戏截图；未在此轮操作游戏逐一试放所有动作。

## 2. 粉紫残留的判断

逐帧扫描了 OpenCV HSV 中 H=125～175、S≥65、Alpha≥8 的候选像素，并保存最大候选帧号、位置和数量。候选不是确诊：

- cast_debuff 的紫烟、cast_attack_2 的紫剑光不能清掉。
- 人物与鞋子周围附着的窄粉紫线、离散点，才是重点污染区域。
- cast_special 即便使用正确普通 Alpha 显示，仍可见部分紫边，因此**只修预乘不够**。
- hurt 普通 Alpha 下边缘较轻，游戏混合错误进一步放大了残留。
- cast_prayer 第 49 个时间线 key 的粉紫候选最多（1362 个）；需要区分贴体污染与原金色效果的暖色边缘，不建议整图按色相清除。

## 3. 上一轮祈祷修复的不足

v55 确实修改的是 `cast_prayer`，游戏日志也确认调用了该名字，不能把用户仍看到问题归咎于资源路径。

v55 的提取器曾默认所有旧图集都是预乘格式，而此次证明旧祈祷图集并非如此。对普通 Alpha 纹理直接反预乘会把半透明 RGB 放大并裁切，之后再预乘也无法恢复原颜色。因此 v55 的中段清理不能作为可靠最终版本。

下一轮应从未经过这次反预乘的原始 RGBA / 原旧图集重建祈祷，不要继续在 v55 上反复清色。首尾替换为 idle 只证明端点相同，不能证明接近端点的运动与配色连续。

## 4. GIF 排查

旧 hurt 灰底 GIF 和对应 RGBA 首帧按同样灰底、同样缩放重新合成后比较：

- 旧 GIF 无透明索引，42 帧。
- RGB 平均绝对误差约 0.317，单通道最大误差 47；调色板量化确实会改变局部边缘色。
- 所有帧延时为 10ms，总计 420ms，而标称动作时长是 450ms。

旧祈祷透明 GIF 导出代码直接对 RGBA 使用自动调色板，并指定 `transparency=0`。GIF 只有一个完全透明色索引，不能表达 PNG 的多级半透明；自动调色板、透明索引、缩放和帧 disposal 必须单独验证。即使所有 PNG 正常，透明 GIF 也可能出现阶梯边、颜色边和残影。

此次为每个动作生成了按游戏混合公式、固定深灰背景的 GIF 及逐帧 PNG。它避开透明 GIF 的语义歧义，但仍有 256 色量化限制。60 FPS 在 GIF 中只能以 10/20ms 延时交替近似，不是每帧精确 16.667ms；PNG 的 60fps 抽样时间线更适合精确检查。

建议后续交付保留：RGBA PNG、深灰/浅灰不透明 GIF、MP4；透明 GIF 作为附加预览，不当作游戏边缘质量的唯一判断依据。

## 5. 建议修复顺序

1. 先按附件来源明确普通 Alpha / 预乘 Alpha，统一游戏图集为预乘格式；不能把已有预乘动作再乘一遍。
2. 对人物轮廓做局部颜色去污染，保留正常粉紫技能效果，避免靠全局侵蚀删掉手脚和剑。
3. 重建祈祷中段；处理特殊施法和 hurt 的贴体边缘。
4. 用当前 idle 统一每段**站立首尾**的人物比例、头部和双脚落点。必要时修尾段过渡，禁止在最后一帧突然改 scale。
5. 优先复核 cast_attack_1、cast_attack_2、cast_special；其余小偏差也逐一检查，不忽略。
6. 用真实游戏混合方式复核深/浅背景，最后再重新制作 GIF 并回读验证颜色、透明和帧延时。
7. 测试通过后更新冻结记录，再打包；里角色资源不动。
